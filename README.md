## Встановлення (PowerShell, з папки проєкту)

Перевірено на Python 3.15.0. Потрібні Python, Git та доступ до PyPI для встановлення.

```powershell
cd C:\Users\crmpm\PycharmProjects\ai-agents-lab1-git
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

У вже налаштованому проєкті повторно створювати .venv не потрібно. Якщо ключа ще немає, скопіюйте `.env.example` у `.env` і заповніть `GROQ_API_KEY`. **Не перезаписуйте наявний .env.** Ключі та реальні персональні дані не додаються до Git. Модель: `openai/gpt-oss-20b`, провайдер Groq. Без ключа детерміновані тести працюють; AI live дає 503, ручний шлях працює. Виклики live можуть витрачати квоту провайдера.

## Повна відтворювана перевірка

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe scripts/verify.py
```

Друга команда запускає два власні процеси API: fixture на `127.0.0.1:8011`, live на `127.0.0.1:8012`, запускає notebooks у справжніх Jupyter kernels та зберігає outputs. HTTP-notebook виконується **двічі** без очищення між проходами, щоб перевірити повторюваність. Потім зупиняються лише ці тестові процеси. Поточний сервер на 8000 не зачіпається. Порти 8011/8012 повинні бути вільні; за зайнятого порту команда завершиться з помилкою, не зупиняючи чужий процес.

Лише повторна HTTP-перевірка без 20 викликів A/B:

```powershell
.\.venv\Scripts\python.exe scripts/verify.py --http-only
```

Детерміновані HTTP-помилки роблять notebook неуспішним. Результат live показаний окремо: `failed` — отримано хибну відповідь, `not_run` — провайдер/сервер недоступний, `passed` — відповідь й запис перевірено. Успішне завершення скрипта не означає успіх моделі в кожному випадку: відкрийте підсумкові таблиці. Службові журнали: `.verification-runtime/fixture.log`, `live.log` (не комітяться).

## Звичайний запуск і Swagger

```powershell
$env:AI_MODE="live"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

[Swagger](http://127.0.0.1:8000/docs). Якщо 8000 вже зайнятий вашим попереднім сервером, використайте його або зупиніть його Ctrl+C перед новим запуском.

POST `/videos`:

```json
{"title":"Python","topic":"цикли","duration_minutes":15}
```

POST `/videos/ai`:

```json
{"text":"Відео Python, тема цикли, тривалість 15 хвилин"}
```

GET `/videos` показує записи з UUID. Дані живуть у пам'яті процесу; перезапуск/перезавантаження коду їх скидає. Дублікати дозволені, кожен отримує новий UUID. Використовуйте один worker.

## Запуск notebooks вручну в PyCharm

1. Виберіть інтерпретатор `.venv\Scripts\python.exe`.
2. `01_experiment.ipynb`: Run All, збережіть. Сервіс не потрібний. Не підміняйте фактичні результати моделі очікуваними.
3. Для `02_api_verification.ipynb` запустіть два окремі термінали з кореня проєкту:

Термінал 1 — контрольовані відповіді всередині сервера:

```powershell
$env:AI_MODE="fixture"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8011
```

Термінал 2 — реальна модель:

```powershell
$env:AI_MODE="live"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8012
```

4. Run All у другому notebook, збережіть. Notebook лише звертається через HTTP, ключ йому не потрібний. Timeout=25сек, ліміт провайдера=15сек, retries=0.
5. Повторний Run All перевіряє прирости від початкового стану. Для нового порожнього тестового сховища зупиніть **тестові** сервери Ctrl+C і запустіть їх знову. Жодної бази чи цінних даних не видаляємо.

## Контрольовані сценарії

Лише за `AI_MODE=fixture` назви `FixtureInvalid`, `FixtureWrong`, `FixtureNull`, `FixtureDown` вибирають відповідно неправильний тип, підмінену тривалість, null і збій. Повідомлення лишаються звичайними, наприклад `Відео FixtureWrong, тема цикли, тривалість 12 хвилин`. Сервіс отримує пропозицію 21 й повинен відхилити її. Жодних параметрів обходу в HTTP API немає. У live ці назви не мають спеціального значення.
